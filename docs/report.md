# AI Scientist 评分机制原理与优势解析报告

> 目标：总结本轮开发中对评分机制的完整设计，包括各评分体系的计算原理、维度构成、与迭代闭环的联动，以及每项机制的核心优势。
> 更新日期：2026-08-17

---

## 一、评分体系总览

本项目包含 **两类评分指标** 和 **一套迭代闭环机制**，共同构成质量评估与优化体系：

| 层级 | 指标 | 判定方 | 评分范围 | 回答的问题 |
|---|---|---|---|---|
| 假设质量 | **综合得分（overall_score）** | Critic Agent（LLM 评审） | 0–10 | 这个假设好不好？ |
| 计划细节 | **颗粒度得分（granularity_score）** | 算法计算 | 1–6 | 这个假设够不够具体可操作？ |
| 迭代优化 | **跨轮次评分闭环** | Orchestrator + Critic + Scientist | 与前几轮对比 | 假设有没有越改越好？ |

## 二、评分机制一：综合得分（Critic 智能评审）

### 2.1 维度构成

Critic Agent 从 **五个维度** 对科学假设进行评审（[agent_critic.py 中的 DimensionScores 模型]）：

| 维度 | 含义 | 权重 |
|---|---|---|
| **evidence** | 证据支撑度——假设是否有文献/证据支持 | 0.25 |
| **falsifiability** | 可证伪性——假设是否明确给出可被推翻的条件 | 0.25 |
| **consistency** | 内部一致性——假设内部逻辑是否自洽 | 0.20 |
| **novelty** | 新颖度——假设是否具创新价值 | 0.15 |
| **cross_domain** | 跨学科性——假设是否融合多学科视角 | 0.15 |

### 2.2 加权计算公式

```
overall_score = evidence×0.25 + falsifiability×0.25
              + consistency×0.20 + novelty×0.15
              + cross_domain×0.15
```

- 各维度由 LLM 在 0–10 打分
- 权重体现优先级：**证据支撑与可证伪性是科学假设的第一要务**（合计占 50%），其次是一致性，最后才是新颖度与跨学科

### 2.3 核心优势

1. **多维度、可解释**：单一分数被拆解为 5 个可追溯的子分数，用户在界面上可看到"哪个维度拖了后腿"。
2. **科学导向的权重设计**：将 evidence/falsifiability 权重顶到 0.25，避免"花哨但没依据"的假设得高分——这符合科学方法论优先原则。
3. **LLM 语义评审**：不是机械关键词匹配，而是理解假设的完整语境后打分，能够识别 deep 但表面字数相近的假设差异。
4. **温度可调**：Critic 的 temperature 从 0.5 降到 0.3，在"打分可复现"与"评审有一定多样性"之间取得平衡，降低随机波动。

## 三、评分机制二：颗粒度得分（算法客观计算）

### 3.1 三级计划模型

每条假设的 `plan` 字段包含三级递进的细节层次：

| 级别 | 含义 | 权重 | 示例 |
|---|---|---|---|
| **L1** 概念级 | 方向性描述，无具体数字 | 1 | "通过 do-calculus 进行因果效应识别" |
| **L2** 量化指标级 | 含具体数值/百分比阈值 | 3 | "后门准则满足度 ≥ 95%，混淆偏差 ≤ 5%" |
| **L3** 容错级 | 含备选方案与对照设计 | 6 | "若后门准则无法验证，改用前门准则；设置随机化对照" |

### 3.2 加权计算公式

```
颗粒度得分 = (Σ L1×1 + Σ L2×3 + Σ L3×6) / 假设总数
```

加权逻辑体现 **"具体可操作 > 理论可行 > 泛泛而谈"**：
- L1 只给 1 分——有概念方向是底线
- L2 给 3 分——有量化指标才有可验证性
- L3 给 6 分——有容错/备选方案才称得上稳健的科学设计

### 3.3 分数区间解读

| 分数 | 含义 |
|---|---|
| 1.00 | 所有假设仅停留在概念层（纯方向） |
| 2.00 | 平均达到 L1+L2 水平（有量化指标） |
| 3.33 | L1/L2/L3 三级齐全（当前默认值，见下） |
| 6.00 | 满分，所有假设都有完整三级深层设计 |

### 3.4 核心优势

1. **客观、零成本、可复现**：纯粹由算法按公式计算，不依赖 LLM，同一份假设永远得到同一分数。
2. **公式化、可解释**：分数可直接拆解回"几条带数字的 L2、几条带备选方案的 L3"，方便用户理解为什么是这个分数。
3. **与 LLM 综合评分互补**：综合得分衡量"质量质量"，颗粒度衡量"细节丰富度"，两条线互不干扰，共同给出更立体的评估。

### 3.5 已知边界与优化方向

- **当前瓶颈**：Scientist 的 System Prompt 强制"每条假设都必须包含 L1/L2/L3"，导致统计恒为 3/3/3、得分恒为 3.33，指标暂时失去区分度。
- **优化方向**：将颗粒度统计从"检查有无"升级为"评估内容丰富度"——例如 L2 要求"含数字 + 足够长度"，L3 要求"含备选/对照关键词 + 足够长度"，使敷衍的二级计划无法拿满分，真正拉开分数差距。

## 四、评分机制三：跨轮次迭代评分闭环

### 4.1 迭代链路（V1 → V2 → V3）

```
V1 跑完 → 写入 snapshots/V1.json（含 Critic 全部评审 + overall_score）
        ↓
V2 开始时 → Orchestrator 读取 V1.json，提取 critic_output + overall_score
        ↓
     注入 Scientist Prompt ← 结合上一轮 Critic 评审意见
       ↓
V2 跑完 → Critic 得到 prev_scores(V1) → 对比验证改进是否到位
        ↓
       输出 📈提升 / ⚠️退化 对比日志
        ↓
V3 同理，V3 为最大迭代上限（边界保护）
```

### 4.2 两大核心设计

**① Critic → Scientist 的改进传导**
Orchestrator 在 V2/V3 开始时读取上一轮快照，把 Critic 的 **五维评分、top_flaw（致命缺陷）、missing_evidences（缺失证据）** 注入下一轮 Scientist 的 Prompt，并在 Prompt 中给出"目标至少提升 0.5 分"的明确要求。

**② Critic 的跨轮次纵向评审**
Critic 在评审当前轮时收到 `round_label` 和 `prev_scores`，会**对比上一轮分数**，验证"新增改动的假设是否真的比上一轮好"，同时在 Prompt 中注入"不得放水"的硬约束。

### 4.3 核心优势

1. **从"重跑"变成"修正"**：之前的迭代是每轮独立生成假设（Scientist 不知道上一轮哪里被骂），现在是"上一轮的错误显式传给下一轮"，真正实现有记忆的迭代优化。
2. **可观测的迭代效果**：每轮结束打印对比日志，运营同学能直观看到评分是提升还是退化（如 `📈 V2 评分较上一轮提升 0.85 分`）。
3. **闭环验证**：Critic 不只是"再打一次分"，而是"确认这次改进是否真的到位"，避免假设越改越偏。

## 五、评分机制的联动关系图

```
                      ┌──────────────────────────────────────┐
                      │          Agent 流水线执行一轮         │
                      │  Explorer → Scientist → Critic       │
                      └──────────────────┬───────────────────┘
                                         ↓
                    ┌────────────────────┼────────────────────┐
                    ↓                    ↓                    ↓
           综合得分 (Critic)       颗粒度得分 (算法)      快照持久化
           五维权重加权           L1/L2/L3 加权          JSON文件 + DB表
                0–10                 1–6
                    └────────────────────┼────────────────────┘
                                         ↓
                          ┌──────────────────────────────┐
                          │  下一轮迭代开始（V→V+1）       │
                          │  读取上一轮快照 → 注入         │
                          │  Scientist AND Critic         │
                          └──────────────────────────────┘
                                         ↓
                             评分对比 → 提升/退化日志
```

## 六、结论与最佳实践沉淀

1. **评分必须多维**：单一的 LLM 分数可解释性差，拆成独立且权重明确的维度（evidence/falsifiability 优先）让系统更可信。
2. **客观指标 + 主观评审并用**：LLM 综合分保证深度，算法颗粒度分保证公平，两者互补。
3. **迭代 = 修正，而不是重跑**：跨轮次传递上一轮评审，是让"迭代真的在变好"的关键基础设施。
4. **指标要有区分度**：颗粒度恒为满分说明"必填约束 + 有无判定"的组合会破坏指标价值，需要把硬约束改成梯度评分。
5. **天然防止退化（改进建议）**：当前 V3 已实现上一轮注入与对比日志；如需更强保障，可为综合得分加"单调约束"（若低于上一轮 ×0.95 则自动重评一次，取两次最大分）。

# 文献处理体系：双源供给 + 向量统一 + 生命周期分层

> 新增章节：总结本轮开发中对文献检索、入库、清理全链路的设计构想，涵盖向量库架构、切分策略、临时文献回收机制，以及前端示例问题动态化的改造。
> 新增日期：2026-08-25

## 1 核心设计原则

项目文献处理部分的构想可概括为：**「双源供给 + 向量统一 + 生命周期分层」的 RAG 知识库设计**。其四条底层原则为：

1. **双源供给，统一汇入**：本地 PDF 与在线 arXiv 两个入口，汇入同一个 Chroma 向量库；
2. **source 标签为文献身份**：承担去重键、引用溯源、清理定位三重职责；
3. **生命周期分层**：长期种子永久保留，pipeline 临时检索的文献用完即删；
4. **切分策略适配内容形态**：摘要模式保持语义完整，全文模式靠 overlap 衔接上下文。

## 2 双源供给架构

```
papers/*.pdf ──seed_pdf.py──┐
                            ├→ Chroma (knowledge_base) ←── Explorer 向量检索(top-k)
arXiv API ──PaperSearch─────┤        ↑                      │
  ↑ 临时(用完即删)          │        └── 长期(永久保留)      ↓
  └── pipeline 运行时 ──────┘                          evidence_list → Scientist → Critic
```

| 来源 | 入口工具 | 用途 | 生命周期 |
|---|---|---|---|
| 本地 PDF（papers/ 目录） | `scripts/seed_pdf.py` | 长期知识库：Science 125 问题清单、各领域综述 | 永久保留 |
| 在线 arXiv | `PaperSearchService.search_and_ingest()` | pipeline 运行时按问题实时检索的临时证据 | 本次 pipeline 结束即清理 |

两个入口共享统一的 Paper 数据结构（`paper_search_service.Paper`），通过 `to_chroma_document()` 转成 `content + metadata` 格式，下游 Agent 不关心文献来源，只做语义检索。

## 3 Chroma 向量库的「身份标识」机制

每条 chunk 的 `metadata.source` 是整个文献体系的核心标识，承担三重职责：

- **去重键**：`seed_pdf.py` 按 source 判断是否已入库，保证重复运行安全幂等；
- **引用溯源**：Explorer 的 `evidence_list` 每条都带 source，Critic 可验证证据真实性；
- **清理定位**：按 source 批量删除特定文献（如临时 arXiv 文献）。

典型 source 值示例：
- `"Science_2025"` — Science 125 问题清单（人工语义化命名）
- `"physics_ybco_2024.pdf"` — 用户手动添加的领域综述（文件路径命名）
- `"arxiv:XXXX.XXXXX"` — pipeline 临时检索的 arXiv 论文

## 4 临时文献的「快照 diff 精确清理」

为避免在线检索的临时论文污染长期知识库，设计了「策略 B：快照 diff 精确清理」：

```
pipeline 开始 → 快照现有 arxiv_id 集合（pre_ids）
            → 按问题检索 + 入库新文献
            → post_ids - pre_ids = 本次新增
pipeline 结束 → cleanup_by_arxiv_ids(新增) 精确清理
```

这样实现：
- 用户手动塞入的种子文献（按 `Science_2025` 等 source）**永久保留**；
- pipeline 临时检索的 arXiv 论文（按 `arxiv:ID` source）**跑完即回收**，保证下次运行时检索环境干净。

## 5 切分策略

使用 LangChain 的 `RecursiveCharacterTextSplitter`，默认参数为 chunk_size=1200、chunk_overlap=100。针对两种内容形态做差异化处理：

- **摘要模式**（在线 arXiv 论文默认）：标题+摘要整条一个 chunk，保留完整语义；
- **全文模式**（本地 PDF）：切成多 chunk，靠 100 字符 overlap 衔接上下文，避免切分断裂。

## 6 跨领域类比锚点的三层设计

除正式文献外，`src/config/seed_data.py` 中的 `DEFAULT_SEED_DATA` 承担「跨领域类比锚点」的角色——在向量库为空或检索不到相关文献时，为 Explorer 提供跨域方法学桥梁。

适合放入锚点的内容：100-200 字、聚焦「方法学核心」而非具体事实、明确标注可类比的其他领域。当前覆盖 4 个不相关领域（统计物理、复杂网络、神经科学、因果推断），建议扩展至 6 类以覆盖 Science 125 的主要范式。

## 7 前端示例问题动态化改造

**原问题**：前端 `web/app.js` 硬编码 8 条示例问题，领域集中在物理/统计/因果推断，仅 1 条与 Science 125 清单对齐，且不与 Chroma 知识库联动。

**改造方案**：从 Chroma 的 `Science_2025` 文献中动态提取 125 个问题条目。

### 后端：问题提取服务

新增 `src/services/question_service.py`，实现「按行扫描 + 领域跟踪 + 断行合并 + 前缀清洗」的四步提取策略：

| 步骤 | 实现 | 说明 |
|---|---|---|
| 1. 领域标题行跟踪 | 正则匹配 "Mathematical Sciences" 等 14 个领域标题 → 映射为中文 | 为每个问题标注所属领域 |
| 2. 行缓冲拼接 | 不以句末标点结尾的行与后续行拼接 | 处理 PDF 断行截断的标题（如 "regenerated?" 单独一行） |
| 3. 前缀清洗 | 循环剥离页码/页眉/黏连领域名 | 去除 "125 QUESTIONS"、"Science/AAAS" 等噪声 |
| 4. 归一化去重 | 仅保留小写字母的 hash 作为 key | 避免同一问题的不同截断版本重复 |

提取结果在进程内缓存，只计算一次。API 为 `GET /api/questions`，返回 `{total, questions: [{id, category, question}]}`。

### 前端：动态加载 + 兜底

- 原 8 条硬编码示例降级为 `FALLBACK_QUESTIONS` 兜底；
- 弹窗打开时异步调用 `/api/questions`，成功后替换 `sampleQuestions` 并重建领域下拉框；
- 后端不可用时静默回退到兜底示例，不影响使用。

### 实测效果

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 问题数量 | 8 条 | **114 条** |
| 领域覆盖 | 3 个（物理/统计/因果） | **10 个**（数学/化学/医学/生物/天文/物理/神经/生态/能源/AI） |
| 与知识库关联 | ❌ 不联动 | ✅ 全部来自 Chroma Science_2025 文献 |
| 搜索过滤 | 不支持 | ✅ 按关键词（如 "cancer"）实时过滤 |

## 9 经验沉淀与最佳实践

1. **向量库需要分层**：长期知识（种子/PDF）和临时证据（arXiv 检索）必须在生命周期上明确区分，避免检索环境污染；
2. **source 是文献的身份证**：单一字段承担去重、溯源、清理三重职责，设计时应优先定义好命名规范；
3. **种子数据要克制**：`DEFAULT_SEED_DATA` 应只保留 15-20 条跨域锚点，超过阈值的文献应走 `seed_pdf.py` 入库；
4. **PDF 提取用按行扫描**：基于行的扫描比正则分句更稳健，能天然处理 PDF 断行；
5. **前端示例必须联动知识库**：硬编码示例与实际知识库脱节，会导致 Explorer 对示例问题检索不到证据，系统性压低评分；
6. **兜底机制不可少**：任何动态化改造都应保留静态兜底，避免服务故障时前端白屏。
